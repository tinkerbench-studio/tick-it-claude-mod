# Set up review agents

When a ticket is built (`/tick-it done`), tick-it runs each review skill in `.tick-it/skills/<name>/SKILL.md` whose sizes match the ticket and whose `paths` match at least one file changed against the merge base (all of those that match the size when the changed files cannot be listed) as a subagent of this session; a skill left out is recorded as not applicable. From round 2 a skill that was clean runs again only when it has a blocking finding still open or a file changed since the previous round matches its paths (a clean one is recorded as not applicable and its verdict carries forward). Their blocking findings come back to be fixed, and the ticket is Done after a clean round with every acceptance check ticked, except those flagged after-deploy (any other check left unticked asks a person). A repository with none has no review: the ticket goes straight to Done, with a reason on the move (a ticket with no merged pull request needs one).

1. **Look at what is there.** List `.tick-it/skills`. Keep any skill already there; only add what is missing, and never overwrite one without asking.
2. **Look at the repository.** Its languages, how its tests run (package.json scripts, pytest, go test, a Makefile, the CI workflow), its linters, and anything in CLAUDE.md or the README about how changes are made. If `.tick-it/merge-checks.json` exists, tell the person Tick-it still reads it for compatibility where `.tick-it/config.json` is missing, and that `.tick-it/config.json` with `{ "mergeChecks": [...] }` is the preferred file; point them to `docs/config.md#upgrade` in tinkerbench-studio/tick-it. A repository with no tests yet is fine: say so.
3. **Pick the samples.** The ones named in the arguments, or else all five (leave out `ux-evidence` for a repository with no user interface), which are in the `samples` folder beside this file:
   - `acceptance`: every acceptance criterion is met, and nothing beyond the ticket changed. Every size, a small model.
   - `tests`: the checks run and pass, and each criterion has one that would fail without the change. Every size.
   - `principal`: correctness, design and fit with the code around it. S and up, a larger model.
   - `security`: input handling, secrets, access. M and L, and a ticket of any size whose change touches a security area (authentication, access control, database, infrastructure, secrets, input, web, dependencies, agents, personal data), which it then reviews against that area's `secure-*` skill.
   - `ux-evidence`: a change to what a person sees carries before and after pictures, on its pull request and its ticket, with every visible difference named. Every size, Sonnet. The sample assumes Storybook; fit it to how this repository builds and screenshots its stories, or say that it has none and what stands in for it.
4. **Fit each to this repository.** A sample holds only what is particular to a repository; the rules every repository shares are in its base (`bases/<name>/SKILL.md` beside this file), which the sample names with `base` in its front matter and tick-it puts before the repository's rules when the reviewer runs. Read the base first, so you do not repeat it. Copy the sample to `.tick-it/skills/<name>/SKILL.md` and replace the bracketed placeholders with what this repository has: the real test and lint commands, its conventions, the places that need extra care. Remove a line that cannot apply rather than leaving a placeholder; a skill left with no rules of its own is still worth keeping, for its base. Keep the front matter's `name` and `base`. The `description`, `model` and `sizes` come from the base: add one only to change it (sizes are XS, S, M and L). The `changes` of the `security` base is `all`: every security area runs it whatever the size. Add `changes` to the repository's `security` skill only to fit that: the area names that should run it here (leave out one whose words this repository uses for something else), with globs of its own sensitive paths beside them (`changes: all, src/billing/**`), or `changes: none` for size alone. Add `paths` for a skill that applies to some files only (globs on one line, separated by commas or spaces; left out, every path). The `principal` base tells its reviewer to `recall` conventions and cite an M-id, which needs the Tick-it tools in the reviewer: for a repository whose reviewers have none, say in its `principal` skill to leave that out.
5. **Show what you wrote**: each skill, its sizes and model, and what you fitted. Do not commit: the person decides.

Each reviewer reports `BLOCKING:` and `OPTIONAL:` lines, each with file:line, then `VERDICT: clean` or `VERDICT: changes`; tick-it adds that to the prompt, so the skills need not say it. Blocking is for what must change before the ticket is Done; a matter of taste is optional.

In any text you write into a ticket (a description, acceptance check, comment or note), name another repository's ticket as `owner/name#KEY` and its pull request as `owner/name#n`, never a bare key or `#n`: a bare one always means this repository, and repositories can share a prefix.
