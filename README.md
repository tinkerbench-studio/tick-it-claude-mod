# tick-it, the Claude Code mod

Tick-it in your Claude session. The board comes from Tick-it's MCP server for the repository you are in, read from its GitHub `origin` remote. `/tick-it take <id>` works on a ticket (a Backlog or Ready ticket held until a `notBefore` date that is still ahead (as on Tick-it, a ticket already In progress or In review is not refused) is refused with that date, and nothing is moved or assigned; a Done, Superseded or Dropped ticket is refused as finished, and `take` with no key prints its usage line, calling no Tick-it tool), and `/tick-it done` moves it to In review, with the lines its change touched since it was taken, and **stewards it to completion**.

Every move happens on Tick-it first: take, done, drop, Done after a clean review round with every acceptance check ticked (a check flagged after-deploy is left out), and `/tick-it add`. `/tick-it attach <id> <note> <file>` moves nothing: it attaches a file, such as a log or screenshot, to a note on a ticket's acceptance check (the mod reads it as bytes, so any type up to 3 MB). The board is cached with the repository it was read for, so when Tick-it can't be reached `/tick-it board` shows the last board read for this repository and says why, and nothing moves (a board cached for another repository is not shown).

The manifest points at Tick-it on `https://mcp.tick-it.dev/mcp`. To use a local `tickit-mcp` instead (see the repository README), start Claude Code with `TICKIT_MCP_URL=http://localhost:8787/mcp`. Sign in once with `/mcp`.

## Install

In Claude Code, add the tinkerbench-studio marketplace, then install the plugin from it:

```
/plugin marketplace add tinkerbench-studio/marketplace
/plugin install tick-it@tinkerbench-studio
```

The repositories are private, so Claude Code clones them with your own git credentials (`gh auth login` or a credential helper). For a newer version: `/plugin marketplace update tinkerbench-studio`, then `/plugin update tick-it@tinkerbench-studio` and restart Claude Code. For development, `claude --plugin-dir .` loads it from a clone.

When an edit is refused for passing the size budget, the refusal gives Claude three choices to put to you: raise a new ticket for the extra work (same epic, Backlog, blocked by this ticket), raise this ticket to the next size with `update_ticket` (the guard then measures against the new budget), or leave it as scoped. A ticket already at L has no bigger size, so its second choice is to split it. A ticket with no epic gets its new ticket without one.

The size guard, the status line, the changed lines and files sent with a move to review, the UI-evidence gate and the files the security areas and `changes` reviewers read all count the ticket's change the same way: the working tree (untracked files included) against the commit the ticket was taken at. Once the base branch has been merged into the branch, they count against the merge base of HEAD and the base branch (`origin/HEAD`, else `origin/main`, else `origin/master`) when that merge base is a descendant of the taken commit, so what the merge brought in is not the ticket's change; with no merge since, or no origin branch to find a merge base with, the taken commit is used. A `git diff` that fails in a repository that has a commit gives no count (0 lines); only a repository with no commit yet counts against the empty tree.

What the size guard counts. It estimates the diff after the edit, not the edit alone: the edit's effect is the file's changed lines against the ticket's base after the edit less the same before it (the base text is read with `git show <base>:<path>`), and the edit is refused when the diff so far plus that effect passes the budget. With a readable base, an edit that rewrites lines the ticket added is counted as the growth of the diff, not twice the lines. Where the base text cannot be read (a file new to the ticket, or `git show` fails or exits with an error), the edit's own lines added plus removed stand. An edit that does not make the diff larger (deletions of lines the ticket added, same-size rewrites of them) is never refused, even over budget, and so is one with no readable base whose new text has no more lines than the old (a deletion of a file new to the ticket). A file outside the repository's top level, or one git ignores (`git check-ignore`), adds nothing and is never refused. `replace_all` counts every occurrence in the file, and `MultiEdit` is guarded as the sum of its edits. `NotebookEdit` is not guarded. Any other measuring failure lets the edit through.

Tests: `claude plugin test .` runs the hook tests in `tests/`, and `node --test checks/*.test.mjs` checks the skills' wording. CI runs both.

Shared settings: the size budgets, default review rounds and the brief's instruction lines come from Tick-it's `get_mod_config` tool when a ticket is taken (`hooks/tickit.ts`, `fetchModConfig`). The copies in `hooks/state.ts` and `hooks/board.ts` are only the fallback for when Tick-it cannot answer. The call also sends `repository`, so the answer carries `reviewRounds` and `reviewBudget` for the ticket's size: `reviewRounds` is that ticket's round limit when it is a whole number of 1 or more (otherwise the limit is the repository's `reviewRounds` setting and the defaults, as before), and `reviewBudget` (whole dollars, or null) is the review budget the steward and the brief use ("Review spend budget and the stopping rule" below); both are kept as they were when Tick-it cannot say. Three more brief lines come from `get_mod_config` too, with no local copy: `briefLines.wake` (one line, put in the brief after the `beforeReview` lines: it tells the session to subscribe to its pull request's activity with `subscribe_pr_activity` for Tick-it's wake comments, and what such a comment means; an older Tick-it that does not serve it leaves it out), `briefLines.beforeReview` (an array of lines, put in the brief before the line that says how to finish) and `briefLines.afterFix` (one line, added at the end of the fix prompt in `hooks/reviews.ts`). When Tick-it serves none of the keys, the brief and the fix prompt are the same as without them. The call also sends `modVersion` (`MOD_VERSION` in `hooks/state.ts`), which the server requires; `checks/contract-fixtures.test.mjs` fails when it differs from `version` in `.claude-plugin/plugin.json`. When the mod is older than the server's `minModVersion`, the answer carries a `notice`, and the mod shows that text to you as a toast each time a ticket is taken; a null notice shows nothing. Every `report_session` call the mod makes (taking a ticket, progress, each status change, the typed stop) sends the same `modVersion` too, added where the mod sends the call (`sendTickit` in `hooks/tickit.ts`), so a session shows which mod release reported it; `tests/session-hooks.reports.test.tsx` asserts it equals `MOD_VERSION`.

## Logging

The mod logs the decisions it makes, so a cause can be read afterwards: whether a start line matched, which ticket it took, why a review round started or did not, why a tool call was denied, and each report to Tick-it and each send of review runs from the outbox.

- **Setting:** the environment variable `TICK_IT_LOG`, one of `error`, `warn`, `info` or `debug` (not case-sensitive). A level logs itself and the levels before it. Unset, or any other value, it is `warn`: only errors and warnings are logged, so the log stays quiet.
  - `error`: runs Tick-it rejected.
  - `warn`: a ticket that could not be taken, a report or send that did not get through, a round no reviewer could start, and `held-back-after-clean` (a round settled clean, yet Tick-it still holds the ticket back: its reason is logged, from one get_ticket read; nothing extra is logged when it is not held back).
  - `info`: each report to Tick-it and each send of review runs.
  - `debug`: the decisions above (`start-line`, `ticket-taken`, `start-not-taken`, `round-started` (with `why`: `done-command`, `steward-command`, `moved-by-claude`, `after-fix` or `after-stop`, and `refused`: the reviewers that applied but could not be started, each recorded as a failed run that keeps the round from settling clean), `round-not-started` (with `why`; `head-differs`, `empty-diff` and `other-session-reviewing`, below, log at `warn`), `head-not-checked`, `round-settled`, `tool-denied`), and the session ids behind a report: `ticket-taken` and `report` carry the Claude Code session id beside the Tick-it one, and `outbox-send` logs, for each run sent, the Claude Code session id and the Tick-it one (`none` when no ticket was taken), agentId, skill, round, headSha (`none` for a build or fix turn) and whether Tick-it accepted or rejected it. Each review run is also sent to Tick-it with its `headSha`, the commit its reviewers ran on. No token or header is logged.
- **A denied tool call with no ticket taken:** when the mod refuses `record_runs`, `report_session` or `report_review_agents` and no ticket is current in the session (for example a start line that did not match; not a start line for another repository, whose calls are allowed, see the next line), the reason adds that the mod did not take a ticket in this session, so Claude does not assume its reviews are being recorded.
- **A start line whose ticket could not be taken:** when the take is refused, or the start line names another repository than the folder's origin (`start-not-taken` with `why` `other-repository`; the context line then tells Claude to record and report for itself), the session reports for itself, so the mod allows those three calls (logged as `tool-allowed-untaken` at `warn`) until a ticket is taken. Taking a ticket whose key is known reads just that ticket with `get_ticket`, never the whole board (`list_tickets` is for the board command and pane); a result with no JSON in it is reported with its content blocks and the start of its text.
- **Where:** `tick-it-mod.log` in `TMPDIR` (`/tmp` when it is not set), or the file named by `TICK_IT_LOG_FILE`. The file keeps its newest 1000 lines; the mod rewrites it whole, as the engine writes whole files.
- **What a line holds:** `<time> <level> <event> key=value ...`, only ids, states and reasons (`ticket=TCK-151 why=no-skills`). A value that is not a short token (a title, comment, path or file's text) is replaced with `<omitted>`, and nothing from the environment is logged, not even the level's value. Writing a line never stops the mod: a log that cannot be written is skipped.

## Releases

The marketplace (`tinkerbench-studio/marketplace`) pins this plugin to a git tag, `v<version>`, so an install gets a release and not whatever is on `main`. To release:

1. A pull request leaves `version` as it is. The `Plugin version` check (`scripts/plugin-version.mjs`) fails a pull request that changes `version` in `plugin.json`, `MOD_VERSION` in `hooks/state.ts` or `modVersion` in `tests/contract-fixtures.json`, and passes one that changes `hooks/`, `skills/`, `types/` or `plugin.json` without it.
2. Merge it. When the merge changed one of those paths, the release job (`.github/workflows/release.yml`) raises the patch version in those three files (`scripts/raise-version.mjs`, `.claude/skills/version-raise`), commits that to main, tags the commit `v<version>` and creates a GitHub release; nothing is done by hand.
3. In the marketplace, set `ref` of the `tick-it` entry to `v<version>` and merge that.

Installed copies update only after step 3, and only when `version` changed.

**0.44.0 is the first release that sends ids.** The board matches a ticket to its milestone by epic id (`epicId` of `list_tickets`, `create_ticket` and `update_ticket`, `id` of each epic in `list_milestones`), so two epics with the same title under different owners stay apart, and no hook sends an epic or milestone title to a Tick-it tool (a review run is recorded without its epic). The size guard's new-ticket choice tells Claude to give `create_ticket` the epic's `epicId`. Tick-it can raise `MIN_MOD_VERSION` to 0.44.0.

## Ticket references in replies

**How the mod reads Tick-it.** Claude Code hands a plugin only the content blocks of a tool reply, and replaces one over 50,000 characters with an `Output too large` note, so the mod asks for little. The board is read with `list_tickets` and `slim: true` on every page: each ticket's key, title, status, size, epic and assignee, without its description, acceptance, links or url. A ticket the mod has read whole keeps those across a board read, and every other row takes its url from that pattern (a page address differs only by the key). A ticket only on the board is read whole with `get_ticket` (with `include` `['approvals']`, for the pane's approval request) when it is opened in the ticket pane or taken. Every `get_ticket` the hooks send passes `include`: `[]` (the core: status, acceptance checks, review spend and what holds the ticket back) for the status, the unticked checks, the held-back reason and the review spend, and `['attachments', 'memories']` when a ticket is taken, `['approvals']` when a ticket is taken or opened in the pane, and `['findings']` for the review findings. A reply Claude Code did not pass on whole (`persisted-output`, `truncated-output` or `Output too large`) is reported as too large for Claude Code, not as an answer with no result, and the last board read stays.

A ticket key Claude writes in a reply (`TCK-2`, or the repository's own prefix, in any case) is drawn as a bold link with the ticket's title, `Title (TCK-2)`. Pressing it opens the ticket pane. Only tickets on the board are linked, so `UTF-8` is left alone, and code, fences and links already written are not touched (`linkTickets` in `hooks/board.ts`, drawn by the `AssistantMessage` hook in `hooks/ui.tsx`).

In text written into a ticket or a pull request, a bare key or `#n` always names that text's own repository, and repositories can share a prefix. So the skills that write ticket text (`draft-ticket`, `import-github`, `plan-epic`, `periodic-retro`, `retro`, `revise-plan`, `review-agents`) and the brief of a session tell Claude to write another repository's ticket as `owner/name#KEY` and its pull request as `owner/name#n` (`OTHER_REPOSITORY_LINE` in `hooks/board.ts`; `checks/skills.test.mjs` keeps the skills' wording).

## Pull requests

At `/tick-it done` the mod tells Tick-it the branch the ticket was built on (never the repository's default branch, `origin/HEAD`'s, else `main` or `master`: the ticket still moves to In review) and, if `gh` finds an open pull request for it, its number (`link_pull_request`); a call that does not get through waits and is sent again with the outbox. Tick-it also finds the pull request itself from its description. The Tick-it GitHub App then keeps the ticket's pull request state and CI, and the merge moves the ticket to Done. If clean review rounds find its pull request still open, the ticket stays In review and the mod says it moves to Done when it merges.

The band above the prompt shows the taken ticket's key, title, status and diff against its budget, with a Board button. Pressing the key opens the ticket pane: status, size, epic, milestone, labels, links to the ticket in Tick-it and its newest pull request on GitHub, the description and the acceptance. The mod reads the pull request with `list_pull_requests` at the end of each turn. The board pane lists tickets as a table (key, title with its epic, size, status), grouped by status, with `Waiting until <date>` under the title of a ticket whose `notBefore` hold is still in the future (a passed date or no hold shows nothing; a scheduled job on Tick-it (every 15 minutes) clears a hold itself once its date passes, with a timeline entry, and moves a Backlog ticket to Ready when the release rule allows it (no open blocker or question, autoReady on, its epic in a prioritised milestone, an approved plan, no need), otherwise leaving it in the Backlog, so the marker goes away without anyone editing the ticket) and a `Next to take: <key>` line naming the first Ready ticket that is not held (`heldUntil`, `nextToTake` in `hooks/board.ts`): pressing a title takes the ticket (a held Backlog or Ready ticket is refused with its date, as `/tick-it take` refuses it), pressing its key opens the same ticket pane for it without taking it. The ticket pane shows the ticket's status, size, epic, milestone, pull request and diff (for the ticket taken here), links to the ticket and its pull request, the tickets it waits on and blocks (pressing one shows that ticket; one off the board links to its page), the description, acceptance and labels. While the ticket has an open approval request the pane also shows a `WAITING FOR APPROVAL` section: the request's subject, its items counted by kind (`1 pull-request, 2 picture`), who may answer (`reviewer`), `Waiting <n> days|hours|minutes` and a link to the request on the Tick-it ticket page (`#ar_<id>`); a request Tick-it marks stale (`staleReason` set) shows `Changed since asked: <reason>` instead of the waiting line. The latest answered request shows as `APPROVAL ANSWERED` with its decision (`confirmed`, `rejected` or `rethink`), the person it was asked of, `Answered by: <login>` (`answeredBy`, the person who answered, which can differ from the one asked) and `Answered at: <time>` (`answeredAt`), each left out while null, and each question with its answer. The pane has no Confirm, Reject or Rethink button: answering is on the Tick-it page. The `approvals` part of `get_ticket` is asked for only when a ticket is taken or opened in the pane (`readTicket`), never on the board read, and a reply without it (an older Tick-it) leaves the pane as it was. For a ticket not taken here, `t Start a session on this ticket` starts a Claude Code session on it on this computer (`start_session`) and the pane links to it. When CI on that pull request turns failing, the mod raises a toast naming it (`tick-it: CI is failing on #12 open for TCK-34.`) and opens the pane, once: it speaks again only after CI has left failing and failed anew, or for another pull request.

With a pull request read, the board pane has three actions for it: `f Fix with Claude` puts a prompt in the session asking Claude to read the failing checks with `gh` and fix them within the ticket's size budget (only while CI is failing), `r Re-run failed` runs `gh run rerun --failed` for the newest run of each workflow on the pull request's branch, when that run failed, and `g Open PR on GitHub` opens it with `gh pr view --web`. Each answers with a toast saying what happened or why it failed (no pull request, gh not started, gh's own error).

## Sessions Tick-it starts

Tick-it can start a session for a ticket, on your computer (a `claude-cli://` link with the first message filled in) or in the cloud (your claude.ai routine). That first message begins `Tick-it session s_…: work on <key> in owner/name.` (the key carries the repository's current prefix, `TCK-n` until it is changed): the mod recognises it, takes the ticket, hands Claude its brief with the message, and tells Tick-it the session is working, with Claude Code's session id. As the session goes on it reports its latest word and changed lines (at most once a minute) and every change of status at once: in review, each review round, fixing, waiting, done, stopped. The ticket's page in the web app shows it. Repository names are compared without letter case, as Tick-it does. A first message for another repository takes nothing and says why; it also looks among the folders beside the current repository's top level (`git rev-parse --show-toplevel`) for one whose origin is that repository, and when it finds one it names its path and tells Claude to work there and take the ticket with `update_ticket` (In progress, assignee me), which the mod treats as `/tick-it take`, and the `start-not-taken` debug entry carries it as `checkout` (with none found, or the folders not listable, the line is as before and nothing is taken); in a folder with no origin remote at all (a new project not yet pushed), the mod works on the repository the message names. The line may be indented by spaces or tabs, as a scheduled (routine) session receives it inside its routine-fire-payload block; a mention of it mid-sentence is not a start. A start or continue line counts only while the session has no ticket (none taken with `/tick-it take` or by Claude, and no session started): in a later prompt it is left as text, the prompt goes on unchanged, nothing is taken, moved or reported, and the debug log has `start-line-ignored` with the `ticket` and the `why` (`session-started` or `ticket-taken`); the same line again for the session already started says nothing. A session whose first line could not be taken may still be started by a later one. A first message that begins `Tick-it session s_…: continue <key> in owner/name.` (a routine session for a ticket's conflict, failing CI, failing merge check, released CI fix or a head no review has seen) is a continue line, written and indented the same way: the mod takes the ticket into the session as started, reporting to that `s_…` id, but never moves it (it is already In review or Ready to merge, so its status and assignee stay), reports working to that session and then done (when its turn ends with the ticket In review, after the review round the mod starts; with the ticket Ready to merge, at the turn's end), and records the session's review runs with `record_runs` against it, with `headSha` the pushed head. A continue line for another repository is handled as a start line for another repository is: nothing is taken and the session's own `report_session` and `record_runs` are allowed.

When Claude's `request_review` call (the ticket form, for the ticket taken here, in this repository) succeeds, the mod reports the session `waiting` with `report_session`, and a turn that only reads leaves it waiting: it reports working again only once the diff's changed lines differ from what they were when it began waiting (`waitingLines`), and the end of such a turn sends a waiting report (at most once a minute) so Tick-it can hand back the answer. The answer comes back in `report_session`'s `instructions` (an `Approval request … was answered: …` message, or a stale request to raise again). One that arrives with no turn running is shown as a toast and handed to Claude with the person's next prompt, once, and the session then reports working; one that arrives during a turn is handed over when that turn ends, like any other instruction, and the session reports working as it is handed over. A continue line that carries such an answer takes the ticket without moving it and reports working, and is not treated as a session that is done when its turn ends. Claude's own `record_approval` call is not blocked by the mod: Tick-it refuses it without `approvals:answer`, and Claude sees that refusal unchanged. The pane that shows the request is described above.

**A resumed session** (a cloud session woken after its container was reclaimed, `claude --resume`) comes back as the Tick-it session it was: at `session.start` the mod restores the started session, and with it the taken ticket, the commit it was taken at (the base of its changed lines), where its stewarding stood and a ticket Claude had moved to In review whose review agents had not started. The mod keeps these in its store (`resume-state`, `hooks/resume.ts`), stamped with the Claude Code session id and the repository, and writes them whenever they change; `/tick-it done` and `/tick-it drop` clear the stored ticket and base commit. They are restored only into the session they belong to (same id, same repository): a new session in the same folder, or one in another repository, gets none. A steward in phase `reviewing` is restored as `fixing`, one round back, because its review agents belonged to the old process and none is left to answer: that same round runs again when the next turn ends; one in phase `fixing` starts the next round then. When a started session is restored with no taken ticket and no stewarding to go with it, the mod stops denying that session's own `record_runs`, `report_session` and `report_review_agents` (logged as `tool-allowed-untaken` at `warn`, with `why` `resumed`), as it does for a start line it could not take.

The brief opens with the ticket's description, when it has one, above its acceptance, and tells Claude the acceptance lines are checkable items: tick each one it has met, with a note, and attach a screenshot or other file as evidence to a note on the criterion it proves. When the ticket names a path of the repository's `design.uiPaths` globs and its acceptance does not carry them, the brief adds the repository's own UI-evidence checklist (the `design.checklist` lines of its `.tick-it/config.json`, each beginning "UI evidence:") after the acceptance, with a note to deliver them as the repository's design workflow (`design.workflow`) and its `ux-evidence` review skill describe; a ticket that names none gets nothing added. The mod has no UI paths or checklist of its own: a repository with no `design.uiPaths` gets no lines, and one with no `checklist` gets none either. When the ticket's `notBefore` hold is in the future it adds a `Held:` line naming the date; the ticket pane shows the same `Waiting until <date>`. It also names the tickets this one builds on and the tickets that wait on it, each with its status, from the board's `blockedBy` and `blocks`. When Tick-it gives the ticket a `url` (its page in the web app), the brief also tells Claude to put a link to it, with the key and title, in the description of every pull request it opens for the ticket; when that url's host is loopback (`localhost`, `127.0.0.0/8`, `::1`), a link would mean nothing to a reader, so it asks for the key and title as plain text with no link (`isLoopback` in `hooks/board.ts`). It also asks Claude to name, in `memoriesUsed` when it reports with `report_session`, the recalled memories its plan or change relied on. It tells Claude how to add a finding or follow-up to the ticket: a comment (`add_comment`, `byClaude` true) for discussion, the description (`get_ticket`, then `update_ticket` with the whole description) for lasting detail, and every comment begins with the name of the session that wrote it (its `s_…` id); it also says Tick-it's tools may be deferred and to load them first with `ToolSearch` (`select:mcp__Tick-It__report_session,mcp__Tick-It__get_ticket,mcp__Tick-It__recall,mcp__Tick-It__get_memory,mcp__Tick-It__remember,mcp__Tick-It__record_runs`). The start message says the same, for a session without the mod too, which needs only Tick-it's tools. It also tells Claude that when its ticket needs an open ticket of the repository that must land first, it adds that ticket as a blocker at once with `update_ticket` (`blockedBy`, `session`, `blockerReason`) instead of stopping with `set_needs_human` `blocked-on-decision`; no person approves it. It tells Claude to ask Tick-it for the ticket's branch name with `get_branch_name` before creating a branch, and to reuse an existing branch or open pull request instead of opening another; the start message says the same. It also tells Claude to link every ticket it creates to the ticket it works on straight away, with `add_ticket_link` and a one-line note: `follows-up` for a fix or next step, `caused-by` when the work found the problem, `related` otherwise. It also names the ten security areas and the `secure-*` skill to load before writing or changing code in each (see Secure-coding skills below).

Before a ticket goes to review (`update_ticket` to In review, or `/tick-it done`), the mod checks a branch whose changed files match `touchesUi` (`hooks/ui-evidence.ts`): the repository's `design.uiPaths` globs. A repository with no `design.uiPaths` is never checked: the mod assumes no UI paths, design tool or process of its own, so a repository opts in by setting the `design` section. Pictures are uploaded to Tick-it (`presign_screenshot_upload`, `confirm_screenshot`) and never committed, so the check asks Tick-it for the ticket's pictures with `list_screenshots` and reads none from the repository: no git or gh command looks for them, and the pull request description is not read (whether it lists the pictures and names the visible differences is the ux-evidence reviewer's to judge). It refuses, leaving the ticket taken, when the ticket has no confirmed picture, or when the branch touches a `when` glob of one of the repository's `design.pictures` rules and `list_screenshots` shows no picture whose name matches the rule's `name` glob (tick-it's own rule asks for `board-beside-story-*` when a canvas board changes). A move to In review that Claude made where the mod did not see it (found at a turn's end) is not undone: Claude is told once what is missing, and no review round starts. Each refusal says what is missing, the rule's `why` when it has one, and that the repository's design workflow (`design.workflow`) says how to make the pictures; it names no command or tool, since how a repository draws and pictures its screens is its own. It also says to report a step that cannot run, with its error, rather than write a screenshot script. A story or `.storybook/` change whose every added or removed line only waits, asserts, queries or comments (`waitFor`, `expect`, `findBy…`, `userEvent`, `configure`, a comment or a blank line; `isTestOnlyChange` in `scripts/ui-paths.mjs`) is a test change and counts as no UI path, so it needs no pictures; one other line (an export, `args`, markup, a style) makes it a UI change. It also names each story and page the change touches (a changed file in the import closure of a story in `apps/web/src/design/*.stories.tsx` or a `PAGES` entry of `scripts/page-shots.mjs`, so a shared component touches many; `scripts/ui-touched.mjs`) that has no confirmed picture (each needs `-dark`, `-light` and `-phone`, a page as `<page>-<variant>`, a story as `story-<id>-<variant>`), and refuses until each has one; a repository without those files has none touched. `scripts/ui-evidence-check.mjs` prints the same touched list and, given `--pictures a.png,b.png` or `--pictures-dir <folder>`, fails naming the ones with none. A branch that touches no UI path is not checked, and a check that cannot run lets the move through: when git cannot list the changed files, or Tick-it cannot answer `list_screenshots`, nothing is refused. `/tick-it steward` runs the same check for the ticket being built. The check is `hooks/ui-check.ts`.

The mod also runs the repository's own stale-copy check before the move to In review (`hooks/copies-check.ts`). A repository adds one by giving its `package.json` a `copies:check` script (`"scripts": { "copies:check": "node scripts/copies-check.mjs" }`; tick-it's own, `npm run copies:check`, lists each line that still names a tool, field or setting a change removed or renamed). When the script is there, the mod runs `npm run copies:check` in the repository and, while it exits non-zero, refuses the move (from `update_ticket`, `/tick-it done` or `/tick-it steward`) with the hits it printed (at most 4000 characters); the ticket keeps its status and stays taken. A repository with no `copies:check` script, or no `package.json`, moves to review as before. A check that cannot be started (no `node_modules`, npm not found, or no answer within 120 seconds, or `TICK_IT_COPIES_TIMEOUT_MS` milliseconds when set) does not refuse the move: the move goes through and the pane (and Claude's context, for its own move) says the check could not run.

When the ticket or its epic has attachments, the brief lists each with its type and id (read with `get_ticket` when the ticket is taken) and tells Claude to fetch images (PNG, JPEG, GIF and WebP) with `get_attachment` before building; a PDF is marked as a link Claude cannot read itself. A ticket with none gets no such text.

When Tick-it has recalled memories for the ticket (up to 5, by its epic, its text and the files its blockers changed, read with `get_ticket` when the ticket is taken), the brief lists each with its M-id, kind, strength and status, and marks an unconfirmed one "unconfirmed: check before relying on it"; a ticket with none adds no such lines. The brief also tells Claude to call `recall` before guessing at a convention or decision and `remember` when it learns something a later session would need. The start message carries the same lines.

The brief ends with the repository's instructions for every brief (its owner or an admin writes them on the repository's Settings page in the web app; the mod reads them with `get_repository_settings` when it takes the ticket), when there are any.

Asking Claude in plain words works too ("start on TCK-1"): Claude taking a ticket with `update_ticket` (refused while someone else's live session holds it) is `/tick-it take`, so the brief, the size budget and progress reports follow. Claude moving the ticket to In review is `/tick-it done` only when the call names this folder's repository (letter case aside); the same key in another repository goes to Tick-it untouched. Tick-it keeps a session for it even though it did not start one, and the mod reports to that. Claude is kept off `report_session`, as off `record_runs`. The exception is a breakdown session (`start_breakdown_session`), a temporary suggestion-analysis session (`start_suggestion_analysis`) or a post-deploy check session: its first message starts "Tick-it session s\_…: break down TCK-n" (or "analyse suggestions of TCK-n", or "check TCK-n after deploy"), the mod takes no ticket for it, and that one session may call `report_session` for itself. As with the start line, the line may be indented by spaces or tabs (a scheduled session receives it inside its routine-fire-payload block), and a mention of it mid-sentence does not count. Without the mod, Tick-it still moves the session along with its ticket's status, with no latest word or changed lines.

When a ticket's pull request turns conflicting, Tick-it tells the ticket's live session to merge the base branch in, resolve, run the checks and push. A live session, cloud or local, is told in the reply to a `report_session` (its first report, when it takes the ticket, included), and the mod hands it to Claude as a prompt when the turn ends. A note a person sends a ticket back with (`answer_need`) reaches its session the same way, once: in the reply to the next `report_session` of the live session, cloud or local (or the next session's first, when none is live). A routine only starts a new session, so it is never used to reach a running one; it starts one only for a conflict on a pull request whose session has finished. A session started after the conflict takes the instruction up the same way; one that ended before it got it leaves the pull request flagged and its instruction to the next session. A pull request from a fork, or with a branch name that is not a plain name, is not sent to a session (the text goes into a prompt) and shows as skipped. With no live session, the pull request shows "needs a session" in the web app. Each instruction is on the ticket's timeline.

## Screenshots and the UI evidence check, for any repository

Two scripts ship with the plugin, so a repository does not copy them. Pictures go to Tick-it through `presign_screenshot_upload` and `confirm_screenshot`, never into git. In a repository that is not tick-it, with the plugin installed (its path is `${CLAUDE_PLUGIN_ROOT}`; with `claude --plugin-dir .` it is the clone):

```sh
# 1. Upload the pictures in ./shots for ticket ABC-12: `/tick-it:upload-screenshots ABC-12 ./shots` has Claude do all four steps.
node "${CLAUDE_PLUGIN_ROOT}/scripts/upload-screenshots.mjs" plan ./shots                   # { name, type } of each picture
#    Claude calls presign_screenshot_upload for each and saves url + headers + name in presigned.json
node "${CLAUDE_PLUGIN_ROOT}/scripts/upload-screenshots.mjs" put ./shots presigned.json      # PUTs them, prints what to confirm
#    Claude calls confirm_screenshot for each name printed

# 2. Before review, check a UI change does not commit pictures and that no `<name>-before`/`<name>-after` pair in the pictures folder is identical, which fails with the reason that the sample does not show the change (the branch side only; whether pictures were uploaded is read from Tick-it by `/tick-it done`):
node "${CLAUDE_PLUGIN_ROOT}/scripts/ui-evidence-check.mjs" ABC-12 --base origin/main --pictures-under docs/screenshots
```

The check reads the repository's UI path globs from `design.uiPaths` in `.tick-it/config.json` (the file Tick-it's GitHub App reads; `--config <file>` names another); with none, no path is a UI path and the committed-pictures check passes (the identical-pair check does not read them and always runs) (`scripts/ui-paths.mjs`, the same rule the gate uses):

```json
{ "design": { "uiPaths": ["src/ui/**", "**/*.css"] } }
```

A change touching a `uiPaths` glob fails when it adds or changes a picture file (PNG, JPEG, GIF, WebP) under `--pictures-under` (default `docs/change-screenshots/`). Globs: `**` crosses folders, `*` and `?` stay within one. The mod's `/tick-it done` gate and the brief's UI-evidence checklist read the same globs (from `get_repository_settings`' `config`, the first base branch that sets `design.uiPaths`), so a repository sets them once; with none set, nothing is a UI change. The skill is `skills/upload-screenshots/SKILL.md`. The tick-it repository moving onto these copies is a follow-up ticket.

The acceptance-check conventions (docs, refusal, failure-path and test-coverage checks, and the UI-evidence checklist) are in [docs/ticket-breakdown.md](https://github.com/tinkerbench-studio/tick-it/blob/main/docs/ticket-breakdown.md), section 6. Claude also reads the epic's attached images with `get_attachment` and links each file to the tickets that use it with `link_attachment` (the epic then lists them under used by); it never invents a file and says when a PDF could not be read. The tickets wait in the Backlog until people agree them and move them to Ready. The skill is `skills/plan-epic/SKILL.md`; Claude also uses it when asked to plan an epic.

## Stewarding

Stewarding starts at `/tick-it done`, or when Claude moves its ticket to In review with `update_ticket`, as a session Tick-it started does with no one there to type the command: the mod moves it with its changed lines (in total and per file) and pull request, and the review agents start when that turn ends.

1. Every review skill in the repository whose sizes and paths match the change runs as a subagent of **your own Claude session**: `.tick-it/skills/<name>/SKILL.md`. (Skills still in `.tickit/skills`, where they lived before 0.22.0, are read when `.tick-it/skills` is not there; move them across.)
   Each reviewer is told to review the ticket's whole change against the base: the diff from the merge base with the base branch (`origin/HEAD`, else `origin/main`, else `origin/master`, named in its prompt) to the working tree, untracked files included, so work already committed is reviewed too. With no base branch to find, it is told to review the working tree against HEAD.
2. Each reviewer reports `BLOCKING:` and `OPTIONAL:` lines and a `VERDICT:`. A line is read with the markdown round its marker removed (list bullets, numbers, `#` and `>` marks, bold, italic or code marks, as in `**BLOCKING:**` or `1. BLOCKING:`); a mention of the word after other text is not a finding, a line whose whole body is only a nil word (none, n/a, nothing, no issues, no blocking findings, not applicable; case, punctuation and markdown ignored) such as `BLOCKING: none.` is no finding and counts toward neither total, while `BLOCKING: none of the tests cover X` still is one, and `FINDING:` lines are read the same way. Each is also given the blocking findings its skill raised earlier that are still open (from round 2 the session's own, and in any round the ticket's open ones Tick-it holds), with the head commit, and reports a `FINDING: <number> fixed|open|gone` line with a reason for each; the mod sends these as the run's `verdicts`, so a blocker fixed by hand is marked fixed and one verified open stays blocking. The earlier findings are this session's own and the ticket's open required findings that Tick-it holds (`get_ticket` with `findings`, from any session), merged per skill with none given twice; a verdict on a Tick-it finding carries its `finding` id, and a skill with one open runs whatever its paths and is never carried forward or settled as already reviewed.
3. Blocking findings go back to your session as a prompt to fix. When that turn ends, the reviewers run again: a fix is never left unreviewed. After the round past the limit (see step 4) the mod asks for no more fixes for a reviewer's findings (a round whose only blocking findings are the pull request's own is the exception, in step 4), so none is left unreviewed; Tick-it also flags any ticket whose newest fix is later than its newest review and refuses to take it to Done.
4. A round is clean only when every reviewer that ran finished and said `VERDICT: clean`: a run whose turn did not end with an answer, an answer with no `VERDICT:` line, and `VERDICT: changes` with no `BLOCKING:` line that could be read are not a clean review. Such a run is saved as failed (it has no clean verdict to carry forward) and the reviewer is started again once in the same round; if the second run gives none either, the steward stops (`stoppedBy` mod), reports the typed stop `reviewer-no-verdict` with the need (kind `no-clean-round` and a note naming the skill; see "The typed stop") and leaves the ticket In review. When another reviewer of that round left `BLOCKING:` lines, those go to Claude to fix as usual and the failed reviewer runs again in the next round. A run whose agent was lost, or that the stop button ended, is not started again: the round stops the same way, with a note that does not say twice. A clean round (see "Who does what" below for the pull request's part in it) with every acceptance check ticked by Claude, except those flagged after-deploy (Tick-it reads a review as clean only while every check is ticked, those flagged after-deploy aside; the mod never ticks one itself: a clean round with one unticked first gives Claude a turn to tick the ones it has met, then reviews again, and one still unticked asks a person with `set_needs_human` and leaves the ticket In review) moves the ticket to Done. The limit is the review rounds the ticket's size gets (`reviewRounds` in `get_repository_settings`, read with the repository's instructions when a ticket is taken and as its first round starts, and kept as they were when Tick-it cannot say; by default XS 2, S 3, M 5, L 6), and the pane shows rounds as x/y with y that limit. With a review budget, the band line and the pane heading also show the review spend against it right after the rounds (`round 2/4 · $1.20/$3 · reviewing`, `$3.40/$3 over` at or past the budget; green, amber from 80%, red when over): the `costUsd` of `reviewSpend` that the steward read from `get_ticket` for its budget check, and the kept `reviewBudget`; the pane makes no Tick-it call of its own. With no budget, or before the steward has read the spend (or when `reviewSpend` is null), both lines are as with the round limit alone. When `reviewSpend.afterMerge.runs` is above 0 (review rounds on a head that only merged the base in, which Tick-it keeps out of `costUsd` and the round ceiling; added by tinkerbench-studio/tick-it#TCK-1641, filled by tinkerbench-studio/tick-it#TCK-1643), the pane also shows a line of its own under the heading, `After a base merge: $0.40, 1/2 free rounds` (`afterMerge.costUsd`, then `freeRounds` used of `limit`, the repository's `mergeRounds`); the `$x/$y` figure never includes it. The line needs no review budget: it shows whenever `afterMerge.runs` is above 0, and a later read with no after-merge spend or a null `reviewSpend` takes it off. With zero after-merge runs, no `afterMerge` or a null `reviewSpend`, nothing extra shows. The ticket's own `reviewRounds` from `get_mod_config` is the limit when it gives one. The steward also stops at the review budget (see "Review spend budget and the stopping rule"). When the last round of the limit still has blocking findings, it fixes them and runs one further round (limit + 1), which the ticket timeline marks as past the limit; if that still has blocking findings, it stops and leaves the ticket to you, telling Tick-it the ticket needs a person (the typed stop `rounds-exhausted` with the need, kind `no-clean-round`, the open findings counted in the note). The exception is a round whose reviewers found nothing and whose only blocking findings are the pull request's own (`[ci]`, `[base]`): past the limit it follows the pull-request-only path of the budget case below instead of stopping, so a stop never says a blocking finding is open when no reviewer has one. A clean round whose pull request is still open leaves the ticket In review. If the repository's `autoMerge` setting is on (read with `get_repository_settings`), Tick-it merges the pull request itself and the mod flags nobody; if it is off, or the settings cannot be read, the mod marks the ticket as needing a review of the pull request (kind `review-pull-request`). The merge clears it.

**When a round is not started.** Before any round the mod checks three things, and no reviewer starts and no run is recorded when any fails; the steward stops (the pane and the command's answer say why) and `r review again now` tries again once it is put right:

- **The checkout is not the pull request's head.** `git rev-parse HEAD` is compared with the `headSha` of the ticket's open pull request (`list_pull_requests`), and the message names both commits. When the working tree is clean, nothing on `HEAD` (or on a local branch of the pull request's name) is unpushed, and `git fetch origin <branch>` gives the head Tick-it names, the mod checks out that head itself (`git checkout -B <branch> FETCH_HEAD`), says so in a toast, logs `head-checked-out` at `info` and runs the round, so a session started on another commit (a recovery session Tick-it starts on the default branch) reviews the head without a person. Otherwise the round stops: check out or push the head, then review again.
- **Nothing differs from the base branch.** `git diff` against the base (the working tree, untracked files included) lists no file, so there is nothing to review.
- **Another session is reviewing the ticket.** `list_sessions` (the ticket's build sessions) names another live session whose status is `reviewing`: its round on the head is still being recorded, and a second one would repeat its number and review its own checkout. The message names that session; review again once it has finished. When the sessions cannot be read, the round starts as before.

The round runs as before when the ticket has no open pull request, when the changed files cannot be listed, and when Tick-it cannot be read or gives no head: the pane then says the pull request head could not be checked.

When the repository has milestones, the board pane opens with a header (`◇ <milestone> · 3/9 done · due Nov 6`) read with `list_milestones` along with the board, and shows only the tickets of that milestone's epics. `m next milestone` moves to the next one in roadmap order, then to a last `No milestone` stop for the tickets in no milestone (when there are any), and back to the first. With no milestones the pane has no header and lists every ticket.

While a ticket is stewarded, the board pane has three actions: `r review again now` starts the next round when the current turn ends (also after the rounds ran out or stewarding stopped; with no turn running, a prompt with nothing to fix carries it in), the `o show/hide optional` button shows or hides optional findings, and `s stop stewarding` ends the rounds and leaves the ticket In review. `r` and `s` are reported in the session's status updates. When Tick-it suggests breaking the ticket down (after several review rounds in a row that each end with blocking findings), no further fix round starts: stewarding stops with a note, the ticket stays In review, and Claude is handed the suggestion to offer to you; `r` starts the next round if you decline. When the mod stopped stewarding itself (the round limit or the review budget, not the `s` button) and Claude then pushes a fix and moves the ticket to In review again with `update_ticket`, that fix is reviewed once when the turn ends (as the next round; this one review goes past the round ceiling and the review budget, as a fix already made is always reviewed once) and the session reports the outcome: `done` when it and the pull request are clean; with reviewer findings still open (a round whose reviewers found nothing and whose only finding is the pull request's own is fixed and read again instead) the mod stops again, calls `set_needs_human` with kind `no-clean-round` and starts no further round. Stewarding stopped with `s` is not restarted by a move to In review; `r` starts it. A review run counts as running only while its agent can still answer: `r` and the end of a round first mark a running run failed when `$.agent.list()` does not show its agent running, `session.start` marks a running run of another Claude session failed, and a new round (`/tick-it steward` or `r`) marks running runs of earlier rounds failed, so a late answer from one changes nothing; none of these failed runs is sent to Tick-it (how a round with a failed run settles is TCK-54's). The pane lists the round's blocking findings by file and line. The pane reads findings the session already holds and sends nothing new to Tick-it; the counts are the ones recorded with the round's runs, and a line says how many findings are not listed.

### The typed stop, the round verdict and the check-in

These parts need a Tick-it that has the stop contract (`report_session`'s `stop`, docs/cloud-sessions.md "The stop contract" in tinkerbench-studio/tick-it, tinkerbench-studio/tick-it#TCK-1594); the parts that read `roundVerdict`, `waitingOn`, a resume instruction and `sessionStopped` act only on a Tick-it that answers them (tinkerbench-studio/tick-it#TCK-1595 to tinkerbench-studio/tick-it#TCK-1598), and against one that answers none of them the mod behaves as it did before.

- **The typed stop.** A stop by the mod (each `stoppedBy: 'mod'` stop) and the `s` button are one `report_session` call: status `stopped`, a `stop` (`code`, with `skills`, `round` and `head` where known) and the need (`needsHuman`: kind `no-clean-round`, or `session-stopped` for the button), never a report followed by `set_needs_human`. The codes: `reviewer-no-verdict` (a reviewer gave no verdict twice; `skills` names them), `ci-pending` (CI not confirmed for the checked-out commit, or still pending after a fix), `rounds-exhausted`, `budget`, `pull-request-blocking` (the pull request still blocks after the fix with no reviewer round left), `other` (a finding still open after two fix rounds) and `person-stopped` (the `s` button). When the call does not get through, the whole report, need included, is kept and sent again with the outbox (`/tick-it sync`, or the next send of runs). A session with no Tick-it session to report to (a folder with a ticket taken by hand and no session Tick-it kept) still asks for the need with `set_needs_human`, as before.
- **The round verdict.** When the `record_runs` answer carries `roundVerdict` (`clean`, `blocked`, `incomplete` or `running`, as a word or as an object holding it and the reviewers it names in `skills`) and `next`, `settleRound` follows it instead of its own reading: `clean` is a round with no blocking finding (the pull request and the acceptance ticks still decide), `blocked` asks Claude for a fix (with `next`), `incomplete` runs the named reviewers again, once each, and does not stop, and `running` waits. With no `roundVerdict` the mod reads the round as before.
- **The check-in.** At turn end on a ticket In review, before the session goes idle, the mod reports and reads `waitingOn` from the answer: with `session` it submits `next` as the next prompt (the same `next` at most once in a row, so an instruction the session cannot meet does not loop); with `person`, `queue`, `reviewers` or `nothing` it goes idle and the stewarding pane says which. A `resume` in the answer (a `resume` field, or an instruction starting with the word) starts the next round, as `r` does, when the mod stopped stewarding; when you pressed `s` it is ignored and the pane says so. The `reviewing` report the new round makes is the acknowledgement.
- **A stopped Tick-it session.** A `sessionStopped` in the answer of `set_criterion_checked`, `add_criterion_note` or `record_runs` is shown in the pane and queued as an instruction for Claude: its Tick-it session is stopped, so it must not tell you the ticket will merge, and the next turn end resumes it.

No review skills means no review: `/tick-it done` takes the ticket straight to Done (with a reason on the move, since no pull request has merged for it). `/tick-it:review-agents` has Claude set some up in `.tick-it/skills`, fitted to the repository, from five samples that come with the mod (`skills/review-agents/samples`), each of which names its base (see Base review skills below) and holds only the repository's own rules: `acceptance` (every size, Haiku), `tests` (every size, Sonnet), `principal` (S and up, Opus), `security` (M and L, and any size whose change touches a security area, Sonnet) and `ux-evidence` (every size, Sonnet: a change to what a person sees needs before and after Storybook screenshots on its pull request and ticket). Each sample also tells its reviewer that accepted findings are not raised again: a finding of the ticket a person decided accepted (listed in its prompt with its id) is not raised as BLOCKING or OPTIONAL and not with a verdict of open, and a new finding with different text still is.

A review skill (`paths` lists the globs of the files it applies to: on one line separated by commas or spaces, as an inline list (`["src/**", apps/**]`, entries quoted or not) or as a block list (`- src/**` lines under `paths:`); `sizes` and `changes` are written the same ways; a brace group (`src/**/*.{ts,tsx}`) is written out as one glob per alternative before the line is split, and `report_review_agents` sends that expanded list; a glob that still holds a bracket, a brace, a quote or a leading `!` can match no path, so it is left out and named in the line that starts the round, and a skill whose globs are all left out applies to every path; a skill with no `paths`, or an empty one, applies to every path, and the mod reports each skill's globs to Tick-it with `report_review_agents`; Tick-it records them. A round lists the files changed against the merge base with the remote's default branch (`git merge-base HEAD origin/HEAD`, then `origin/main` or `origin/master`; uncommitted and untracked files count as changed) and runs a skill only when its sizes match the ticket and, if it has `paths`, a changed file matches one of its globs (a skill with no `paths` always runs); a skill left out because no changed file matches its paths is recorded on the round as not applicable (`notApplicable`; one whose sizes leave out the ticket is not recorded), and when none applies the ticket moves to Done with that reason. When the files cannot be listed, every skill that matches the size runs. From round 2 a skill that reviewed the ticket runs again only when it has work left: a blocking finding of its own still open (one Tick-it holds counts, whichever session raised it, and the skill then runs whatever its paths), or a file changed since the previous round's reviewed commit that matches its paths (any changed file, for a skill with no `paths`); one that was clean (a reviewer whose last run did not finish has no verdict to carry and runs again) and finds neither is recorded on the round as not applicable with that reason, its clean verdict carries forward, and the round that would move the ticket to Done counts it as clean. When none has work left, no reviewer starts and the round settles as any round whose reviewers found nothing: the pull request (a failing one asks for a fix) and the acceptance checks decide. A steward run starting at round 1 runs every skill that applies (as before, one whose head was already reviewed clean with the pull request and acceptance checks settled starts none, unless a skill still has an open finding in Tick-it). A glob matches at any depth unless it starts with `/`, which reads it from the repository's top, as Tick-it reads it; `**/` crosses folders, `*` and `?` stay in one):

```markdown
---
name: principal
description: Second principal engineer on every change
model: claude-sonnet-5-5 # optional; the session's model otherwise
sizes: S, M, L # optional; every size otherwise
changes: authentication, database, src/billing/** # optional; the kinds of change that run it whatever the size (see Security areas below)
paths: apps/mcp/migrations/**, docs/** # optional; globs on one line (commas or spaces), an inline list or a block list; {ts,tsx} groups are expanded; every path otherwise
---

What to check, in your own words.
```

### Base review skills

The plugin ships a base for each of the five roles, in `skills/review-agents/bases/<name>/SKILL.md`: `acceptance`, `principal`, `security`, `tests` and `ux-evidence`. A base holds the rules that are the same in every repository and none that belongs to one. Every reviewer prompt begins with the ticket's size (`Ticket size: S.`), which the `principal` base reads: in round 1 of a ticket sized S, M or L it lists, for each changed action, its failure paths, what a second concurrent call does and what input it accepts, before it reports findings; an XS ticket keeps the lighter pass. A repository's own skill adds its rules to a base by naming it in its front matter:

```markdown
---
name: principal
base: principal
---

- BLOCKING: a break with our conventions: hooks live in `hooks/` and register through `hooks/register.tsx`.
```

When the round starts, the mod reads the base from its own folder and gives the reviewer the base first and the repository's rules after it, as rules that add to the base and are the ones to follow where the two differ. The `description`, `model` and `sizes` a skill leaves out are its base's, and so is its `changes`; `name` and `paths` are always the skill's own, and those are what `report_review_agents` sends. So a repository keeps only what is particular to it, and a change to a base reaches every repository with the next release of the plugin. A skill with no `base` is read whole, as before. A `base` this version of the plugin does not have (the name is a folder name: lower-case letters, digits and hyphens) changes nothing in the skill, which reviews by its own rules alone, and the line that starts the round says so.

Every base also says, for each round: fetch the base branch before judging what the diff contains; on lines unchanged since round 1 a later round raises BLOCKING only for a correctness or security defect, with why it was missed, and anything else found late is OPTIONAL; wording is BLOCKING only when it states something false about behaviour, a count or a name, and text the change did not touch never is; a line that says nothing is wrong (none, not needed, listed only to say the check was done) is not reported, and a check the reviewer could not run in its own sandbox is not BLOCKING. Each base names what it owns so one defect is raised once: `acceptance` the criteria, `tests` the tests, `principal` the code and its documents, `security` access and input, `ux-evidence` what a person sees; a defect another base owns is left to it. `acceptance` decides what must exist and `ux-evidence` decides how it is worded and drawn, and the other's contradicting finding is OPTIONAL.

The base is put in by the mod. A session without the mod (one that stewards from Tick-it's own instructions) reads only the file in `.tick-it/skills`, so there a skill with a `base` reviews by the repository's rules alone.

### Security areas

Size is not the only thing that runs a reviewer. A review skill that lists `changes` in its front matter also runs on a ticket outside its `sizes` when the change touches one of the kinds of change it lists. The `security` base lists `changes: all`, so an XS ticket that edits sign-in, a query, a role check or a workflow file is reviewed for security, and an XS ticket that edits a label is not.

An entry of `changes` is the name of a security area, `all` for every area, or a glob of the repository's own sensitive paths (an entry with a slash, a dot or a star, read like `paths`: `**` crosses folders). `changes: none` turns it off, so the skill runs by size alone whatever its base says. An entry that is none of these is named in the line that starts the round (`changes` may be a line, an inline list or a block list). A skill with no `changes`, and no base that has one, runs by size as before.

The areas, and what puts a change in each (`hooks/security-areas.ts`), read from the changed paths and the added and removed lines of the same diff the size budget measures (since the ticket was taken, with untracked files):

| Area | Covers | Skill |
| --- | --- | --- |
| `authentication` | sign-in, sessions, passwords, tokens, account recovery | `tick-it:secure-authentication` |
| `access-control` | permissions, roles, scopes, ownership, tenants, admin | `tick-it:secure-access-control` |
| `database` | SQL, queries, migrations, schema files | `tick-it:secure-database` |
| `infrastructure` | Terraform and other infrastructure as code, CI workflows, containers, platform and runtime configuration | `tick-it:secure-infrastructure` |
| `secrets` | keys, tokens, environment secrets, encryption, hashing, signatures | `tick-it:secure-secrets` |
| `input` | shell commands, file paths and uploads, server-side fetches, redirects, webhooks, parsers | `tick-it:secure-input` |
| `web` | HTML built from data, cookies, CSRF, CORS, security headers | `tick-it:secure-web` |
| `dependencies` | manifests, lock files, registries, a dependency line of a `package.json` | `tick-it:secure-dependencies` |
| `agents` | prompts, tools, MCP servers, hooks, agent permissions | `tick-it:secure-agents` |
| `personal-data` | personal data stored, logged, sent, exported or deleted; analytics and consent | `tick-it:secure-personal-data` |

A path can put a change in an area by its name (`auth/`, `migrations/`, `*.tf`, `.github/workflows/`); so can a word on a changed line (`password`, `SELECT … FROM`, `innerHTML`). Prose and pictures (`.md`, `.txt`, `.svg`, a `LICENSE` and the like) put a change in no area. In lock files, tests and fixtures (a `test/` or `fixtures/` folder, a `.test.` or `.spec.` file) only the path counts and words are not read: a test that signs in changes no sign-in, and the code it tests is read for itself. The reading is made without a model and is a first guess: it decides that the reviewer runs and what it is told to look at, never what it finds. A repository whose own words collide with an area (a product that calls its conversations "sessions") lists the areas it wants in its `security` skill's `changes`.

The reviewer is told what the change touches, with the files that say so, to review those parts first and by what they are, and is given the practices of each area touched: the body of that area's `secure-*` skill, read from the plugin's own folder. A "Must" there that the change breaks is a blocking finding, a "Should" an optional one. A skill running for its size gets the same when the change touches an area it lists. When a skill runs only for what the change touches, the line that starts the round says so (`security runs for what the change touches: authentication, database.`), and the reviewer is told the ticket is outside its sizes. Once a skill has reviewed a ticket it stays eligible for every later round of it, so a fix that takes the change out of an area still has that round's findings answered; from round 2 it runs only while it has a blocking finding open or a changed file matches its `paths` (a clean one is carried forward, as above), and `changes` areas do not count as work left.

`report_review_agents` sends Tick-it each skill's `sizes` and `paths` as before, and not its `changes`: Tick-it does not yet know that a skill can run outside its sizes, and leaves a run of a skill whose `sizes` leave out the ticket's size out of what holds the ticket back. The mod's own rounds are not affected (its blocking findings go back to be fixed, and the ticket is Done only after a clean round), but Tick-it's own reading of such a ticket does not count that run until the server takes `changes` too.

### Secure-coding skills

The ten `secure-*` skills in the table above are part of the plugin (`skills/secure-<area>/SKILL.md`). Each holds the practices for one area as "Before you write", "Must", "Should" and "Check before review", for any application and no one repository. They are for the session that writes the code as much as for the reviewer:

- Each skill's description says when to use it, so Claude loads it before writing or changing code in that area, in a session with or without a ticket.
- The brief of a taken ticket names the ten areas and how the skill of each is named (`SECURE_CODING_LINE` in `hooks/security-areas.ts`, the mod's own line, not one `get_mod_config` serves), and says that the security reviewer checks the change against the same skill.
- The first edit of a ticket that lands in an area (by the edited file's path, or the words of the edit) adds a line to that edit's result naming the area and its skill, once per area for a ticket (`hooks/tool-hooks.ts`).
- The security reviewer is given the body of the skill for each area the change touches, so the author and the reviewer work from one text.

What is particular to a repository (where its sign-in lives, the helper every query goes through) stays in its own `.tick-it/skills/security/SKILL.md`, which adds to the base as before.

### Who does what: the steward, the CI instruction and the merge queue

A round is clean only when its reviewers found nothing **and** its pull request is neither failing CI nor stale (behind its base or in conflict; a queued pull request is exempt from that, the queue updates it). The steward reads the pull request (`list_pull_requests`: `ci`, `behind`, `mergeState`, `mergeQueue`, `ciInstructed`) when the reviewers are clean and adds blocking findings of its own:

- **CI failing** is a blocking finding. A fix is followed by another review round, which is also what the merge queue wants: it drops an entry whose CI fails on the head commit, and the ticket rejoins only after a clean review and CI on a new commit. When `ciInstructed` is true, Tick-it's own CI instruction (sent once per head commit, after all checks finished) has already told the session about this commit: the steward's fix prompt says to follow that instruction and not to start a second, separate fix; the review round after that turn decides. A new push clears it.
- **Behind its base or conflicting**, and not in the queue: the steward merges the base into the PR branch (`git merge`, never a rebase, amend or force-push), runs the checks, pushes, and reviews again. This is what the backend's conflict instruction says too.
- **In the merge queue:** the queue owns the branch. Only the queue head is brought up to date, by the queue, with the repository's update method, and a commit the queue did not make takes the entry out of the queue. The steward never merges the base into a queued branch or updates it; it acts on a queued branch's conflict only through Tick-it's conflict instruction. The one push it makes there is a fix for failing CI, which the queue has already taken the entry out for.
- **Failing CI or a stale branch alone does not stop a round at the review budget or the round limit.** When the reviewers found nothing and the only blocking findings are the pull request's own (`[ci]`, `[base]`, `[pull-request]`), neither the budget nor the round limit stops the round: Claude is asked for the fix, which needs no reviewer spend to confirm, and the pull request is read again after it. Where the budget allows another reviewer round, the fix is reviewed as above. Where it does not, no review agent starts and no spend is recorded: the round settles on the pull request alone, clean only when the pull request is open, CI has passed and the branch is not behind or conflicting (with the acceptance checks ticked as usual), and otherwise stopped with the typed stop `pull-request-blocking` and the need (kind `no-clean-round`). CI still **pending** (or a pull request that is missing, closed or has no CI report) after the fix is never read as clean: the steward stops with the typed stop `ci-pending` and the need, naming the pending check, and `r` reads the pull request again (while the budget has no room, still without a reviewer) once CI has finished. The same path serves a round past the round limit (or the review of a fix made after a stop): the round limit does not stop a round whose reviewers found nothing, it asks for the fix and settles on the pull request alone. A stop on the pull request's own finding names it in the `no-clean-round` note (`CI is failing on pull request #n`, `pull request #n is behind its base`) rather than counting blocking findings. CI that Tick-it reports as failing while it gives no head commit, or a head other than the checked-out commit, is not a finding: it is CI not yet confirmed (a reading taken right after a push still shows the previous head's result). The pull request is read once more, and if it is still unconfirmed the steward stops with `set_needs_human` kind `no-clean-round` and a note that names the CI; `r` reads it again. A round with reviewer findings still stops at the budget and at the round limit as before.
- **Pending CI** does not block a round: the steward does not wait on it. The backend tells the session when it fails, and the merge queue and Done (which waits for the pull request to merge) hold the ticket until CI passes.

A pull request the steward cannot read counts as a blocking finding too: the round is not clean until Claude has checked it with `gh`. These findings go to Claude in the fix prompt only; they are not part of any review run, so the pane's counts and finding list do not show them. They are added only when the reviewers found nothing; a round with reviewer findings is fixed first.

The cloud steward (the brief of a session Tick-it starts on claude.ai) follows the same rules, step 5 of its procedure.

## Time and cost

For each reviewer run, tick-it records the following from its `turn.complete`:

- wall-clock time
- the four token counts
- the model

The cost is what those tokens would cost at API list prices. On a Claude plan they count against the plan's usage instead. Prices are in `PRICES` in `hooks/state.ts`, and a model with no price there shows `—`.

`/tick-it reviews [id]` shows each run, then totals by reviewer and overall. The history is kept in the mod's store across sessions (the last 500 runs). Each run carries the repository it was made in, and the list, the round numbers and the earlier blockers read only this repository's runs (names compared without regard to letter case); runs of other repositories are counted apart. A run an older mod stored with no repository belongs to the repository it is first read in.

## Re-checking fixes and the repeated finding

Each extra round re-runs every applicable reviewer, and in a week of tickets 15 of 70 blocking findings in round 3 and later were the same defect raised again because its fix was incomplete (TCK-80). Two behaviours keep that loop cheaper:

- **The session checks its own fixes first.** The brief (`RECHECK_LINES` in `hooks/board.ts`) tells the session, before it asks for another review round, to go through each blocking finding it fixed and confirm against the finding's text and the current diff that it is fixed, and to fix it again rather than ask for a round when it is not. It also tells the session that after a merge of the base branch into the ticket's branch it re-checks the findings earlier rounds confirmed fixed, since a merge can undo a fix. The brief states this; the mod does not check that the session did it.
- **A finding still open after two fix rounds goes to a person.** The steward counts, per skill, file and text, how many rounds a blocking finding has stayed open: its first appearance is 1 and each later round that verifies it open (a `FINDING: <n> open` verdict) adds one; a round of the skill that lists it fixed or gone starts the count again. When a finding reaches 3 (raised, then still open after two fixes, `FIX_ROUNDS_PER_FINDING`), the mod asks for no further fix or round: the steward stops (`stoppedBy` mod) and calls `set_needs_human` with kind `no-clean-round`, naming the finding (its Tick-it id when `get_ticket` has one, the skill, the file and the text). A finding raised again as a new `BLOCKING:` line is a new finding and counts from 1. A person's `decide_finding` (accepted or fix) restarts the count: the mod reads the decision from `get_ticket` (findings) when a finding is about to stop the rounds, and counts only the rounds from the one it first saw the decision in, so a finding decided before that round counts that round once. The count reads this session's recorded runs only: after a restart in a fresh container it starts from the runs the mod has stored.

## Review spend budget and the stopping rule

Besides the round limit, Tick-it can give a ticket a review spend budget: what review and fix may spend on it, in whole dollars, by ticket size (`reviewBudgets` in `get_repository_settings`, next to `reviewRounds`). A repository whose owner has set no figure uses the defaults, which are the 75th percentile of what finished tickets spent, rounded up:

| Size   | XS  | S   | M   | L                        |
| ------ | --- | --- | --- | ------------------------ |
| Budget | $1  | $3  | $5  | none (rounds limit only) |

The owner can change them with `set_repository_settings` (`reviewBudgets`); setting a size to `null` puts it back on its default. How they were worked out is in Tick-it's `docs/review-budgets.md`.

**How spend is measured.** Spend is the `costUsd` of the ticket's review and fix runs added up, the runs this mod records with `record_runs` (see "Time and cost": the four token counts priced at API list prices). Build runs are not counted. A run with no price is left out of the sum and counted as unpriced, so the figure is a lower bound when any run is unpriced. Tick-it reads it back as the ticket's `reviewSpend` (`costUsd`, `budget`, `remaining`), which `get_ticket` returns; it is null for a caller who cannot see costs.

**The stopping rule.** The review rounds stay a ceiling alongside the budget: the budget never raises the number of rounds, and a ticket with no budget is limited by rounds alone. A session runs another round only while blocking findings are open, spend is under the budget and the round count is under the ceiling (the size's `reviewRounds`, plus the one further round after the last, as described in "Stewarding"). Before a further round it reads `reviewSpend` and does not start a round whose cost, judged by the rounds so far, would clearly overshoot `remaining`; with `reviewSpend` null it goes by the rounds alone. A fix already made is still reviewed once first, even after the ceiling or the budget stopped the steward: the one review of a fix moved to In review after such a stop (see "Stewarding") runs past both, and if it still has blocking findings the mod stops again and asks a person. When either the budget or the rounds run out with blocking findings still open, the session fixes nothing more (except a round blocked only by its pull request: see "Who does what"), calls `set_needs_human` with kind `no-clean-round` and a note naming the budget or rounds and the open findings, and leaves the ticket In review for a person. `continue_reviews` lifts both the ceiling and the budget for that one ticket until a round is clean.

The mod's steward applies both. Once a round has blocking findings and the round ceiling allows another, and the ticket has a `reviewBudget` (`get_mod_config`), it reads `reviewSpend` with `get_ticket` (it reads it without a budget too, to keep `afterMerge` for the pane) and starts no further round when `remaining` is used up or the average cost of the rounds so far is more than `remaining`. It stops as at the ceiling (the ticket stays In review, the typed stop `budget` with the need, kind `no-clean-round`, a note naming the budget and the open blocking findings), and asks for no fix, so none is left unreviewed; the exception is a round whose reviewers found nothing and whose only blocking findings are the pull request's own, which is fixed and settled on the pull request alone ("Who does what"), past the round limit as well. With no `reviewBudget` (the read then only keeps the after-merge spend for the pane line), with `reviewSpend` null (costs cannot be seen) or with `get_ticket` unreachable, it goes by the round ceiling alone. The brief of a ticket with a budget carries the same words, pull-request exception included; the start message of a session Tick-it starts without the mod does not carry the exception yet (it is worded in Tick-it's own repository). A round settled on the pull request alone is not counted in the average cost of a round.

**Rounds across sessions.** Review rounds belong to the ticket, not to the session. The first round a session starts on a ticket (`/tick-it done`, `/tick-it steward`, or Claude's own move to In review) is numbered after the larger of the highest round number Tick-it has recorded for it (not the count of entries: Tick-it refuses a duplicate round number) and the highest round this session already ran, plus one (so a record still waiting to be sent never has its number reused) (`get_ticket_timeline`, review entries), so a second session's first round is round 2 when one ran before, and the round ceiling counts the ticket's rounds. A round does not start while another live session of the ticket reports `reviewing` (`list_sessions`, see "When a round is not started"): that session's round on the head is still being recorded. The review of a fix continues from the session's own round. The budget check divides `reviewSpend.costUsd`, which covers every session, by the number of review entries recorded for the ticket, not by this session's count. When every review skill that applies to the ticket has a recorded run on the current head commit with no blocking finding (a skill's newest run, the last in the timeline, is matched by the `headSha` of its agent in that timeline entry; a run recorded as not applicable counts when it names the head too), no reviewer starts: the round settles from the pull request and the acceptance ticks alone (from `/tick-it done` or `/tick-it steward`, which cannot ask Claude to tick a check or fix CI, only when that settle ends clean; otherwise the head is reviewed as usual). The skip also needs a clean working tree (`git status --porcelain` empty): reviewers read uncommitted and untracked edits too, so the commit alone does not say what was reviewed. A different head is reviewed as usual. **A merge of the base needs no review when its review carries over.** After a merge of the base into the branch is pushed and CI has passed, Tick-it records that the head only merged the base and the review of the earlier commit carries over: `list_pull_requests` then gives `reviewCarriedOver` true for the ticket's pull request (added by tinkerbench-studio/tick-it#TCK-1468). The mod then starts no reviewers, whatever the round, and settles the round from the pull request (CI, the branch) and the acceptance ticks, as above (from a command, only when that settle ends clean, and only with a clean working tree); the stewarding pane says `Review carried over from the earlier commit <short hash>`, the hash being the newest head a recorded review run names. With `reviewCarriedOver` false or absent (an older Tick-it), the round runs as before. When the timeline cannot be read, the mod behaves as before: the session's own highest round plus one (round 1 on a fresh session), and a review; entries that name no `headSha` still carry the round numbering and the budget, and are never taken for the current head.

## Reporting to Tick-it, from local and cloud sessions

What `/tick-it done` does, how it differs from `report_session` with `done`, and how a session finishes the same way with `update_ticket` is written in [Finish a session](https://github.com/tinkerbench-studio/tick-it/blob/main/docs/cloud-sessions.md#finish-a-session-tick-it-done); the brief points to it.

Tick-it is an MCP server, and this mod lists it in `.claude-plugin/plugin.json` as `tickit`. Each finished run goes to its `record_runs` tool as soon as the run lands: every review agent, and every main-loop turn spent on a ticket, as a build turn while the ticket is taken or a fix turn while a review round's findings are being fixed. That way a ticket's cost covers building, reviewing and fixing. A cloud session's container, and the mod's store with it, is thrown away when the session ends, which is why runs aren't held until later.

- **Signing in:** the mod holds no token; the call uses the session's own MCP connection.
  - On your machine, sign in once with `/mcp`.
  - In cloud sessions, add the Tick-it connector on claude.ai. The session reaches it through that connector, so no Allowed domains change is needed.
- **Cloud sessions load the mod from the environment's setup script:** a project's `extraKnownMarketplaces` and `enabledPlugins` in `.claude/settings.json` are not applied in a cloud session, and a SessionStart hook would install it too late for that session. Add these to the cloud environment's setup script:

  ```sh
  claude plugin marketplace add tinkerbench-studio/marketplace
  claude plugin marketplace update tinkerbench-studio
  claude plugin install tick-it@tinkerbench-studio
  claude plugin update tick-it@tinkerbench-studio
  ```

  The plugin's own `tickit` server cannot connect there (the sandbox proxy answers `mcp.tick-it.dev` with 403, and the mod holds no token), so the mod falls back to the claude.ai connector, whose tools a cloud session lists as `mcp__Tick-It__*` (server name `Tick-It`). With the mod loaded, runs carry the real input, output and cache token counts; the start message tells a session without it to record runs itself.

- **What it sends:** the Claude Code session id (`session`), the Tick-it session's `s_…` id (`tickitSession`, when the session took a ticket; left out otherwise, such as a person's own local session), the repository's `origin` URL, and the runs. Each run carries its time, token counts, model, cost, where the session runs (`place`: `cloud` when the connector a cloud session lists, `Tick-It`, took the call; `local` when the plugin's own server or a local session's `claude.ai Tick-It` connector did), the number of blocking and optional findings, and each finding with its file, line and text, and each verdict on an earlier finding (with the finding's Tick-it `finding` id when it came from Tick-it) (read from the reviewer's `BLOCKING:` and `OPTIONAL:` lines, with any markdown round the marker removed, clipped to 2000 characters, 200 to a run). Tick-it keeps them so `get_ticket` can show them; a reviewer should not put secrets in a finding.
- **Batch size:** the waiting runs go in calls of at most 100 runs each (Tick-it accepts at most 500 a call and refuses a larger one whole). A call that fails leaves only its own runs waiting; the other calls still go.
- **What Tick-it answers:** `{ accepted: [agentId], rejected: [{ agentId, reason }] }`.
  - Accepted runs leave the outbox.
  - Rejected runs are dropped and listed under "Dropped" in `/tick-it reviews` with Tick-it's reason, because sent again they would only be rejected again.
  - A run the answer doesn't mention stays waiting.
- **When the call fails as a whole** (not signed in, server down, an error result): every run stays waiting. They go with the next finished run, at session start and end, and on `/tick-it sync`. A session sends only the runs of its own repository: the runs of others stay waiting, and `/tick-it sync` counts them. Tick-it keys a run by its `agentId`, so a run sent twice counts once.
- **The model can't write runs:** the mod refuses the model's own calls to `record_runs` and `report_review_agents` (the mod sends the repository's review skills itself at session start). Tick-it's other tools (tickets, epics, costs) are the model's to use.

**Asking for an approval.** A session that needs a person's approval pushes its branch, calls `request_review` naming each item to approve, and ends its turn; the brief says so, and says a chat reply such as "I approve" is never an approval (it is answered with the link to the request on the ticket page). Once Tick-it has the request the mod reports the session `waiting`, and the ticket pane draws a WAITING FOR APPROVAL section (subject, items by kind, who may answer, how long, a link). When the request is answered, Tick-it's answer to the session's next `report_session` carries it: a toast if no turn is running, and the answer goes to Claude with the next prompt (see "A session that waits for an approval" in [docs/cloud-sessions.md](https://github.com/tinkerbench-studio/tick-it/blob/main/docs/cloud-sessions.md) for the delivery order). The pane's APPROVAL ANSWERED section shows the answer until the session has taken it, that hand-off, and not after.

**Answers are given only in the Tick-it web app.** The mod and Claude never hold the `approvals:answer` scope, so neither can answer a request: the pane is read only, and Claude's own `record_approval` is refused by Tick-it.
